# Requirements Document

Family Story Night is a Fire TV web application that generates personalized, illustrated bedtime stories for families.

## Introduction

Family Story Night is a Fire TV web application that generates personalized, illustrated bedtime stories for families. Users enter family member names and select a theme, and the system generates a 6-page story starring those family members. The story is displayed page-by-page on a TV screen with warm, book-like styling and is narrated aloud using natural voice synthesis. The application is designed for Fire TV remotes, providing a comfortable, distraction-free storytelling experience suitable for family bedtime routines.

## Glossary

- **System**: The Family Story Night application (backend + frontend)
- **User**: A family member or caregiver interacting with the app via Fire TV remote or keyboard
- **Story**: A 6-page personalized narrative generated by Claude via AWS Bedrock
- **Page**: A single section of a story, containing 2-3 sentences of narrative text
- **Narrator**: AWS Polly neural voice engine (Joanna) that synthesizes speech
- **Theme**: A predefined category that influences story content (e.g., "a cozy adventure")
- **Fire_TV_Remote**: A directional remote control with arrow keys, Enter, and Back buttons
- **Setup_Screen**: The initial interface where users enter names and select a theme
- **Loading_Screen**: A transient interface shown while the story is being generated
- **Story_Screen**: The main display interface showing one page at a time with narration controls
- **Bedrock_API**: AWS service providing Claude model for story generation
- **Polly_API**: AWS service providing neural text-to-speech narration
- **Page_Turn_Animation**: A visual transition effect when navigating between story pages

## Requirements

### Requirement 1: Story Generation from Family Input

**User Story:** As a parent, I want to enter my family's names and select a theme, so that the system generates a personalized bedtime story featuring my family.

#### Acceptance Criteria

1. WHEN the User launches the application, THE System SHALL display the Setup_Screen
2. WHEN the User enters family member names in the input field, THE System SHALL accept comma-separated names
3. WHEN the User selects a Theme from the available options, THE System SHALL display the selected Theme name
4. WHEN the User presses Enter or clicks "Begin the story", THE System SHALL submit the family member names and selected Theme to the backend
5. WHEN valid family member names are provided, THE System SHALL send a POST request to `/generate-story` with familyMembers array and theme string
6. IF no family member names are provided, THE System SHALL prevent story generation and display an input validation message

### Requirement 2: Story Generation via Bedrock

**User Story:** As the system, I want to invoke AWS Bedrock to generate a 6-page bedtime story, so that I can provide unique, personalized narrative content for each family.

#### Acceptance Criteria

1. WHEN the backend receives a valid story generation request, THE Backend SHALL invoke the Bedrock_API with a detailed prompt
2. WHEN the Backend invokes Bedrock, THE Prompt SHALL include all family member names and the selected Theme
3. WHEN the Backend invokes Bedrock, THE Prompt SHALL request exactly 6 pages of story content
4. WHEN the Backend invokes Bedrock, THE Prompt SHALL specify that each page contain 2-3 sentences
5. WHEN the Backend invokes Bedrock, THE Prompt SHALL instruct the model to use only plain language without dashes, hyphens, or em dashes
6. WHEN the Backend receives a valid response from Bedrock, THE Backend SHALL parse the response into an array of 6 page strings
7. IF the Bedrock response is not valid JSON, THE Backend SHALL fallback to splitting the response into approximate page chunks
8. WHEN story generation completes successfully, THE Backend SHALL return a JSON object with a pages array to the frontend

### Requirement 3: Loading State During Story Generation

**User Story:** As a user, I want to see a loading indicator while my story is being generated, so that I know the system is working and the wait is not a freeze.

#### Acceptance Criteria

1. WHEN the User submits the story generation request, THE System SHALL transition to the Loading_Screen
2. WHILE the Backend is generating the story, THE Loading_Screen SHALL display the message "Turning up the lamp…"
3. WHEN the Backend returns the generated story, THE System SHALL transition from Loading_Screen to Story_Screen
4. IF the Backend returns an error, THE System SHALL transition back to Setup_Screen and display an error message

### Requirement 4: Story Display with Page Navigation

**User Story:** As a user, I want to view the bedtime story one page at a time with clear navigation controls, so that I can read at a comfortable pace on a TV screen.

#### Acceptance Criteria

1. WHEN the story loads successfully, THE System SHALL display the Story_Screen with the first page
2. THE Story_Screen SHALL display the current page's text in large, readable font suitable for TV viewing
3. THE Story_Screen SHALL display the page number and total page count (e.g., "Page 1 of 6")
4. WHEN the User presses the Right arrow key or Enter, THE System SHALL navigate to the next page (if not on the last page)
5. WHEN the User presses the Left arrow key, THE System SHALL navigate to the previous page (if not on the first page)
6. WHEN the User navigates to a new page, THE Page_Turn_Animation SHALL play to provide visual feedback
7. WHEN the User is on the first page, THE Previous page button SHALL be disabled and not clickable
8. WHEN the User is on the last page, THE Next page button SHALL be disabled and not clickable
9. WHEN the User presses Backspace or Escape, THE System SHALL return to the Setup_Screen

### Requirement 5: Audio Narration of Story Pages

**User Story:** As a user, I want to hear each story page narrated aloud in a natural, soothing voice, so that the bedtime story experience is more engaging and immersive.

#### Acceptance Criteria

1. WHEN a new page is displayed on the Story_Screen, THE System SHALL automatically send the page text to the Polly_API
2. WHEN the System invokes Polly_API, THE Request SHALL use the "Joanna" voice with "neural" engine for natural-sounding narration
3. WHEN the System invokes Polly_API, THE Request SHALL request output format as "mp3"
4. WHEN Polly_API returns audio data, THE System SHALL play the audio through the device's speaker
5. WHEN the User navigates to a different page while audio is playing, THE System SHALL pause the current audio and play the audio for the new page
6. WHEN a page's narration completes, THE System SHALL automatically advance to the next page (if not on the last page) after a brief delay of 1200 milliseconds

### Requirement 6: Fire TV Remote Integration

**User Story:** As a user with a Fire TV remote, I want to navigate the story using familiar remote buttons (arrow keys and Enter), so that the experience feels natural and doesn't require learning new controls.

#### Acceptance Criteria

1. WHEN a Fire_TV_Remote arrow key is pressed, THE System SHALL map the key press to standard keyboard events
2. WHEN the User presses Up arrow on the Setup_Screen, THE System SHALL cycle backward through available Themes
3. WHEN the User presses Down arrow on the Setup_Screen, THE System SHALL cycle forward through available Themes
4. WHEN the User presses Enter on the Setup_Screen, THE System SHALL trigger story generation
5. WHEN the User presses Right arrow or Enter on the Story_Screen, THE System SHALL advance to the next page (if available)
6. WHEN the User presses Left arrow on the Story_Screen, THE System SHALL return to the previous page (if available)
7. WHEN the User presses the Back button on the Story_Screen, THE System SHALL return to the Setup_Screen
8. WHEN no valid remote button is pressed, THE System SHALL not perform any action

### Requirement 7: Theme Selection and Display

**User Story:** As a user, I want to select from predefined story themes before generating a story, so that I can influence the tone and content of the narrative without entering custom text.

#### Acceptance Criteria

1. THE System SHALL provide exactly 4 predefined themes: "a cozy adventure", "a magical treasure hunt", "a trip to outer space", "a friendly dragon's forest"
2. WHEN the User views the Setup_Screen, THE System SHALL display the currently selected Theme name
3. WHEN the User views the Setup_Screen, THE System SHALL display a visual indicator (dots) showing which Theme is active
4. WHEN the User changes the selected Theme using arrow keys, THE Visual indicator SHALL update to show the new selection
5. WHEN the User selects a Theme, THE Theme name SHALL be sent to the Backend in the story generation request
6. WHEN the Backend receives a story generation request, THE Backend SHALL include the Theme in the prompt sent to Bedrock

### Requirement 8: Error Handling and User Feedback

**User Story:** As a user, I want the system to inform me when something goes wrong (e.g., backend unreachable), so that I understand why the story cannot be generated and can take corrective action.

#### Acceptance Criteria

1. IF the Backend API is unreachable, THE System SHALL display an error message on the Setup_Screen stating "Couldn't reach the storyteller. Is the backend running?"
2. IF the `/generate-story` endpoint returns an error, THE System SHALL return to the Setup_Screen and display an appropriate error message
3. IF the `/narrate` endpoint returns an error, THE System SHALL log the error and continue playback of the story without audio
4. WHEN an error occurs, THE System SHALL not leave the User in an indeterminate state (e.g., stuck on Loading_Screen)

### Requirement 9: Visual Design and Accessibility

**User Story:** As a user watching on a TV, I want the interface to have a warm, book-like aesthetic with large readable text, so that the experience feels cozy and is easy to read from a distance.

#### Acceptance Criteria

1. THE System SHALL use a warm color palette featuring parchment (light tan), dusk (dark blue), and lamp (warm gold) tones
2. THE Setup_Screen and Story_Screen text SHALL use font sizes suitable for TV viewing (minimum 3xl for body text, 6xl for headings)
3. THE Setup_Screen SHALL display a subtle radial light gradient behind the main content to evoke an ambient lamp
4. THE Story_Screen SHALL display story text in a semi-transparent panel with rounded corners and shadow depth
5. THE Story_Screen SHALL display all text with high contrast against the background for readability

### Requirement 10: Application Initialization and Configuration

**User Story:** As a developer or user, I want the application to start with sensible defaults and configuration, so that the app works with minimal setup.

#### Acceptance Criteria

1. WHEN the Frontend starts, THE System SHALL default the API base URL to `http://localhost:4000` unless overridden by environment variable `VITE_API_BASE`
2. WHEN the Backend starts, THE System SHALL default the AWS region to `us-east-1` unless overridden by environment variable `AWS_REGION`
3. WHEN the Backend starts, THE System SHALL default the Bedrock model to `anthropic.claude-3-5-sonnet-20241022-v2:0` unless overridden by environment variable `BEDROCK_MODEL_ID`
4. WHEN the Backend starts, THE System SHALL require AWS credentials via environment variables (`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`)
5. WHEN the Backend receives a request to `/health`, THE System SHALL respond with `{ "status": "ok" }`

### Requirement 11: Multi-Page Story Persistence

**User Story:** As a user, I want the story to remain consistent as I navigate between pages, so that I can review previous pages without losing context.

#### Acceptance Criteria

1. WHEN a story is generated, THE System SHALL store all 6 pages in memory
2. WHEN the User navigates to a previously viewed page, THE System SHALL display the exact same text without regenerating it
3. WHEN the User navigates to a previously viewed page, THE System SHALL replay the narration for that page

### Requirement 12: Keyboard Input Validation

**User Story:** As a user entering family member names, I want the system to accept comma-separated names and handle edge cases gracefully, so that I can enter names in a natural format.

#### Acceptance Criteria

1. WHEN the User enters names with leading/trailing spaces, THE System SHALL trim whitespace from each name
2. WHEN the User enters empty names (consecutive commas), THE System SHALL filter out empty strings before sending to the Backend
3. WHEN the User enters a single name, THE System SHALL accept it as a valid input
4. WHEN the User enters multiple names, THE System SHALL split them correctly on commas and send as an array
